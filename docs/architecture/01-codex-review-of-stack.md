I disagree with treating this as a 4–6-week beta commitment.

1. **Scope and assumptions.** Defer Turborepo, a separately packaged UI library, live dashboard updates, AI and a general automation builder. Specify dated milestones and explicit beta exclusions. The “confirmed” payment gap overgeneralizes from one FitXpert coach page ([research, line 17](</C:/Users/compuline/Desktop/dawlyy/docs/research/reports/DAWLYY competitor teardown 2026.md:17>)). Pricing also misses [Twilio Verify’s $0.05 per successful verification](https://www.twilio.com/en-us/verify/pricing), additional to channel fees. Model separate environment compute, media egress and backup storage. A database dump does **not** back up uploaded files; add object backups and test their restoration. [Supabase confirms this limitation.](https://supabase.com/docs/guides/platform/backups)

2. **Pick Hono inside Next.js.** Native clients do not require a separate API deployment. Keep the versioned HTTP contract and domain services independent; split deployment when workload, runtime or scaling demands justify it. Server Components must enter through the same authenticated service boundary—direct service reads must not bypass permissions. Co-locate Vercel functions with Postgres. Avoid caching personalized health data until tenant/user cache boundaries are tested.

3. **Keep RLS plus application authorization.** They address different failures: missing tenant filters versus forbidden actions and client assignments. The common failure is cosmetic RLS: Drizzle connects as an owner or `BYPASSRLS` role, and setting JWT claims does nothing to remove that bypass. [Postgres documents this explicitly.](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) Use verified claims, a restricted runtime role and transaction-local context; execute every query through that transaction. Keep current membership checks for revocation because JWT claims become stale. Tenant-only RLS also does not protect client A from client B inside one tenant. Test actual runtime credentials, Storage and Realtime paths.

4. **Automation: narrow the beta first.** Advanced automation is P1 in [the spec, line 530](</C:/Users/compuline/Desktop/dawlyy/docs/spec/DAWLYY_v4_spec.md:530>). For reminders, use persisted due events, pg_cron and Queues with a retrying consumer. For full §31 waits/escalations, I would choose Trigger.dev Hobby; its [$10 includes credits, with usage charges beyond them](https://trigger.dev/pricing). Inngest Free is viable only with a measured execution budget and quota alerts: [executions count runs × (steps + 1)](https://www.inngest.com/pricing). All options need a transactional outbox, idempotent effects, cancellation checks and replay tooling. An event interface does not make in-flight workflow migration easy.

5. **Frankfurt is only one transfer destination.** Inventory Vercel, email, job payloads, analytics, error logs, AI and external backups too. Egyptian database hosting leaves those transfers unresolved. Have counsel determine DAWLYY/coach controller–processor roles, sensitive-data permissions, contracts, minors handling, withdrawal/deletion and applicable permits. [The cited legal analysis](https://cms.law/en/are/legal-updates/egypt-s-pdpl-executive-regulations-issued-one-year-compliance-countdown-begins) describes a 90-working-day application review and uncertain enforcement timing. That can exceed the beta schedule. Supabase Auth, Storage and Realtime also make migration substantially larger than moving Postgres.

6. **The beta gate misses business operation.** [The proposed gate](</C:/Users/compuline/Desktop/dawlyy/docs/architecture/00-stack-decision.md:106>) excludes nutrition and the Action Queue; manual payments have no delivery slice. Require: invite/recovery → package assignment → proof upload → verification/receipt/refund → access activation → published workout/nutrition → check-in review → renewal/freeze/extension with schedule recalculation. Manual payments satisfy [§35](</C:/Users/compuline/Desktop/dawlyy/docs/spec/DAWLYY_v4_spec.md:309>); gateways are unnecessary for beta. Move consent, isolation/entitlement tests, restore verification and Arabic acceptance **before real clients**. Offline acceptance must cover stale edits and account switching, beyond duplicate UUIDs.
