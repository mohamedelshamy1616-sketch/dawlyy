## F1 (RA-001 and RB-001): ordinary sync overwrites logged facts
`logMeal` (`apps/web/src/server/nutrition/logs.ts`) and `saveMeasurements` (`apps/web/src/server/tracking/entries.ts`) upsert on `(tenant, client, client_uuid)` and overwrite an existing, unvoided row's facts (also after 7 days). That bypasses the correction window and history preservation.
Required behaviour: a POST that reuses an existing `clientUuid` of a row that already exists must never change its facts. An identical retry (offline outbox resend) returns the existing row unchanged. A request that differs from the stored row returns the existing row unchanged too, or a 409 `uuid_conflict`: choose one, apply it to both endpoints, and document it in the endpoint's OpenAPI description. Edits go only through `/correct` (replacement INSERT). Also close it at the database: the client runtime role must not be able to change fact columns (values, local_date, status, option, note, free_entry, etc.) of `meal_logs` and `measurement_sets` rows by UPDATE; only the void metadata path and the replacement pointer remain (look at `packages/db/migrations/0006_guards_and_grants.sql` around the client update allowlists at lines ~492 and ~517 and at the guard matrix `packages/db/test/guard-matrix.ts`; if narrowing the grants or adding a guard is the clean way, do that in 0008 and update the matrices). Supplement logs follow the same sync shape: check whether they carry the same flaw and fix them the same way if they are history. Water, metrics are already append-only. Find every caller of these two functions (UI and outbox code under `apps/web/src/lib` and `apps/web/src/components`) and make sure none relies on the overwrite; if one does (for example a status toggle on the same row) switch it to the correction path.
