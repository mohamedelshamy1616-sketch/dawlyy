## RC-001 (high): approval is not bound to the prose the coach saw
`POST /clients/{clientId}/review/{draftId}/approve` takes an empty body and sends the draft's CURRENT text. Another reviewer's save between the coach's read and click changes what is sent. Bind approval to the reviewed content: the approve request must carry the digest (or revision number) of the text the coach is approving, e.g. `expectedTextHash` (sha256 of the exact stored text, computed by the server and returned in every draft response so the client echoes it back), compared under the existing row lock; mismatch returns 409 `draft_changed` with the current draft so the UI can refresh. PATCH of the text must return the new digest. Update the strict approve schema (`apps/web/src/server/review/schemas.ts`), the service, the OpenAPI/response types, and the client (`apps/web/components/review/review-workspace.tsx` and its transport) to send it; the client must show the 409 as a "the draft changed, review again" state, not send. Keep every other approval check. Add API tests: approve with the right digest sends once; approve after another save returns 409 and sends nothing; missing digest is a 400.

## RC-003 (high): common pain wording is not detected
`packages/core/src/safety/lexicon.ts` and `detect.ts`: "عندي آلام شديدة في الصدر" (normalizes to `الام`) and "my knee is painful" produce no flag. Add the missing normalized inflections and plurals for pain, injury and the other lexicon families (Arabic: آلام/الآلام/ألم/وجع/أوجاع with the normalizer's folded forms; English: painful, pains, aching, hurts, hurting, injured, injuries, sprained, swollen and similar), keeping the existing false-positive guards. Add core tests for these sentences and a few negatives that must stay unflagged. Do not widen to words that commonly appear in normal logs (for example "pain au chocolat" style false positives are acceptable to ignore, but "no pain" negation handling must stay as it is today).

## RC-004 (high): flat-weight calorie proposals can never be produced
`packages/core/src/review/proposals.ts:15` needs a weight span of at least 14 elapsed days, but `apps/web/src/server/review/inputs.ts:271` loads `to - 13 .. to` and the review period restricts it further, so the API never supplies 14 days. Give the review a separate rolling weight-evidence window long enough for the rule (load at least 21 days back, independent of the review period), carry it through the core input type, and make sure `canonical.ts` / the input hash covers those samples. Do not change the 14-day rule. Add an API-to-core acceptance test using only dates the real loader can produce (weights spanning 14 or more days before the review end) that yields `lower_kcal_flat` or `raise_kcal_flat`, and one with fewer days that yields none.

## RC-008 (medium): one client's weight history can break the Inbox
`apps/web/src/server/inbox/service.ts:60` aggregates every weight row in the fortnight and `packages/core/src/attention/rank.ts:57` spreads the array into `Math.max` / `Math.min`. Bound the aggregation in SQL (at most one sample per day per client, for example the latest of each `local_date`), and compute extrema with a loop in `rank.ts`. Add a core test with 200000 samples that ranks without throwing, and keep ranking deterministic.
